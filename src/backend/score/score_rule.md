# AI 연애 시뮬레이션 AI 모델 개발 및 DB 연동 정리

## 1. 프로젝트 개요

### 1-1. 프로젝트 목적

본 프로젝트는 LLM과 머신러닝 모델을 결합한 AI 연애 시뮬레이션 서비스이다.

사용자는 AI 캐릭터와 자유롭게 대화하며 관계를 발전시킬 수 있고, AI는 사용자의 발언과 이전 대화 맥락을 바탕으로 자연스러운 응답을 생성한다.

또한 머신러닝 모델을 통해 대화에 따른 호감도와 신뢰도 변화를 예측하고, 점수와 대화 내용을 종합하여 에피소드 진행 및 최종 엔딩을 결정한다.

### 1-2. 전체 시스템 흐름

1. 사용자가 대화 내용을 입력한다.
2. LLM이 캐릭터 성격과 이전 대화 맥락을 참고하여 응답한다.
3. LLM이 대화 내용을 분석하고 머신러닝 입력용 특징값을 생성한다.
4. XGBoost 모델이 호감도 및 신뢰도 변화량을 예측한다.
5. 예측된 변화량을 현재 점수에 반영한다.
6. 점수와 대화 맥락을 바탕으로 에피소드 진행 조건을 확인한다.
7. 최종 에피소드에서는 고백 의도와 관계 상태에 따라 엔딩을 결정한다.

### 1-3. 게임 기본 구조

- 총 3개의 에피소드로 구성한다.
- 에피소드당 5번의 대화를 진행한다.
- 전체 기본 진행은 총 15턴이다.
- 각 캐릭터는 성격 유형과 성별에 따라 구분한다.
- 호감도와 신뢰도는 별도로 관리한다.
- 에피소드 해금 조건을 만족하지 못하면 현재 에피소드를 재도전한다.
- 점수가 게임 종료 기준에 도달하면 즉시 게임을 종료한다.

## 2. 에피소드별 장소 및 진행 방향

각 에피소드는 장소와 상황에 따라 대화 분위기 및 관계 발전 방향이 달라지도록 구성한다.

### EP1. 첫 만남과 서로 알아가기

**장소: 새서울 종로 루프탑 카페**

- 첫 만남을 통해 서로의 첫인상을 형성한다.
- 카페에서 가벼운 일상 대화를 진행한다.
- 서로의 취향, 관심사, 성격 등을 파악한다.
- 사용자의 대화 방식과 반응에 따라 초기 호감과 신뢰가 형성된다.

**AI 대화 방향**

- 처음 만난 사람과 대화하는 자연스러운 분위기
- 부담스럽지 않은 질문과 가벼운 농담
- 상대방의 취향과 관심사를 파악하는 대화

### EP2. 가까워지는 관계

**장소: CGV 동대문 및 청계천**

- 함께 영화를 관람하는 상황으로 시작한다.
- 영화에 대한 감상과 의견을 나눈다.
- 청계천으로 이동하여 산책하며 대화를 이어간다.
- EP1에서 파악한 취향과 관심사를 대화에 활용한다.
- 이전 대화에서 형성된 기억을 바탕으로 친밀감과 신뢰를 발전시킨다.

**AI 대화 방향**

- 영화와 취향에 관한 의견 공유
- 이전 대화에서 언급한 내용을 자연스럽게 기억하고 활용
- 일상적인 이야기에서 조금 더 개인적인 이야기로 확장

### EP3. 진심 확인과 관계의 결정

**장소: 종로 포장마차 거리**

- 포장마차에서 편안한 분위기로 대화를 진행한다.
- 서로의 생각과 감정에 관한 깊은 대화를 나눈다.
- 상대방과의 관계에 대해 진지하게 이야기한다.
- 사용자의 고백 또는 특별한 상황에서 캐릭터의 고백이 발생할 수 있다.
- 대화 내용과 점수를 종합하여 최종 엔딩을 결정한다.

**AI 대화 방향**

- 감정과 관계에 관한 진솔한 대화
- 이전 에피소드의 기억과 관계 발전 과정 반영
- 고백 및 관계 결정 상황에 맞는 자연스러운 응답

## 3. LLM 설계

### 3-1. 캐릭터 페르소나

캐릭터는 크게 두 가지 성격 유형으로 구분한다.

**Type A: 안정형**

- 차분하고 안정적인 대화 스타일
- 상대방의 감정을 고려하는 편
- 관계 형성에 신중한 태도
- 일관된 성격과 반응 유지

**Type B: 즉흥형**

- 자유롭고 즉흥적인 대화 스타일
- 감정 표현이 비교적 적극적
- 예상하지 못한 반응과 상황 발생 가능
- 대화 분위기에 따라 다양한 반응 생성

각 유형은 남성 및 여성 캐릭터로 구분한다.

- Type A 남성 / Type A 여성
- Type B 남성 / Type B 여성

같은 성격 유형은 성별이 달라도 동일한 유형의 머신러닝 모델을 사용한다.

### 3-2. 대화 맥락(Context) 관리

LLM이 이전 대화를 기억하고 일관된 캐릭터를 유지할 수 있도록 다음 정보를 활용한다.

- 이전 사용자 발언
- 이전 AI 응답
- 현재 에피소드 및 진행 상황
- 현재 호감도와 신뢰도
- 캐릭터 페르소나
- 사용자가 언급한 취향과 관심사
- 약속이나 중요한 대화 내용
- 이전 에피소드에서 발생한 주요 사건

대화 맥락은 Streamlit의 세션 정보를 활용하여 관리하며, 실제 게임 DB 연동 시에는 DB에 저장된 대화 기록과 관계 정보를 불러오는 방식으로 확장한다.

### 3-3. 호감도와 신뢰도

관계 상태는 호감도와 신뢰도 두 가지 점수로 구분한다.

**호감도**

- 사용자의 관심 표현
- 칭찬과 긍정적인 반응
- 캐릭터의 취향에 맞는 대화
- 적극적인 호감 표현
- 반복적인 무관심이나 부정적인 반응

**신뢰도**

- 상대방의 감정을 이해하는 태도
- 진정성 있는 대화
- 이전 대화 내용과의 일관성
- 약속과 중요한 내용을 기억하는 행동
- 무성의하거나 신뢰를 떨어뜨리는 반응

호감도와 신뢰도는 서로 독립적으로 변화한다.

### 3-4. 기본 점수 규칙

| 항목 | 초기 테스트 기준 |
|---|---:|
| 초기 호감도 | 20점 |
| 초기 신뢰도 | 20점 |
| 최소 점수 | 0점 |
| 최대 점수 | 100점 |
| 게임 종료 기준 | 호감도 또는 신뢰도 10점 미만 |

각 대화가 종료될 때 XGBoost 모델이 예측한 변화량을 현재 점수에 반영한다.

점수 반영 방식:

- 현재 호감도 + 예측 호감도 변화량
- 현재 신뢰도 + 예측 신뢰도 변화량
- 최종 점수는 0~100 범위로 제한한다.
- 테스트 앱에서는 예측 변화량을 정수로 변환하여 적용한다.

### 3-5. 에피소드 해금 조건

다음 에피소드로 이동하려면 호감도와 신뢰도 조건을 모두 충족해야 한다.

| 진행 구간 | 호감도 조건 | 신뢰도 조건 |
|---|---:|---:|
| EP1 → EP2 | 45점 이상 | 40점 이상 |
| EP2 → EP3 | 70점 이상 | 65점 이상 |

에피소드 종료 후 두 조건을 모두 충족하면 다음 에피소드를 해금한다.

둘 중 하나라도 기준에 미달하면 다음 에피소드는 해금되지 않는다.

### 3-6. 재도전 규칙

- 해금 조건을 충족하지 못하면 현재 에피소드의 첫 번째 턴부터 다시 시작한다.
- 재도전 횟수에는 제한을 두지 않는다.
- 재도전 시 해당 에피소드가 처음 시작했을 때의 호감도와 신뢰도로 복구한다.
- 이전 에피소드의 진행 기록과 중요 기억은 유지한다.
- 재도전 과정에서도 대화에 따른 점수 변화와 해금 조건을 다시 확인한다.

단, 호감도 또는 신뢰도가 게임 종료 기준인 10점 미만으로 떨어지면 재도전 여부와 관계없이 게임을 즉시 종료한다.

### 3-7. 게임 종료 규칙

다음 조건 중 하나라도 발생하면 게임을 종료한다.

- 호감도가 10점 미만으로 떨어진 경우
- 신뢰도가 10점 미만으로 떨어진 경우

게임 종료 시점의 점수와 대화 기록을 보존한다.

게임 종료 후에는 에피소드 진행 및 재도전을 할 수 없다.

### 3-8. 고백 규칙

EP3에서는 고백과 관계 결정 과정을 진행한다.

**기본 원칙: 사용자가 먼저 고백한다.**

- 사용자의 대화에서 고백 의도를 LLM이 판단한다.
- 캐릭터는 현재 호감도와 신뢰도, 이전 대화 맥락을 바탕으로 응답한다.
- 점수가 충분하지 않거나 상황이 적절하지 않으면 거절하거나 관계 발전을 보류할 수 있다.

**예외: 캐릭터의 선고백**

- 기본적으로 사용자가 먼저 고백하는 구조를 유지한다.
- 단, 호감도와 신뢰도가 충분히 높고 대화 맥락상 자연스러운 특별한 상황에서는 캐릭터가 먼저 고백할 수 있다.
- 캐릭터의 선고백은 기본 진행이 아닌 특별 이벤트로 취급한다.

**고백 참고 기준**

| 항목 | 초기 테스트 기준 |
|---|---:|
| 호감도 | 85점 이상 |
| 신뢰도 | 80점 이상 |

위 기준은 고백 가능성을 판단하기 위한 초기 테스트 기준이며, 점수만으로 고백 결과를 결정하지 않는다.

### 3-9. 최종 엔딩 규칙

최종 엔딩은 호감도와 신뢰도뿐 아니라 대화 내용, 고백 의도, 양측의 관계 수용 여부를 종합하여 결정한다.

| 엔딩 | 조건 및 방향 |
|---|---|
| 연인 엔딩 | 서로 연인 관계를 받아들이는 경우 |
| 썸 엔딩 | 서로 호감은 있지만 관계를 확정하지 않고 발전을 보류하는 경우 |
| 친구 엔딩 | 연애 관계로 발전하지 않고 친구 관계를 유지하는 경우 |
| 고백 거절 엔딩 | 고백에 대해 명확하게 거절하는 경우 |
| 관계 종료 엔딩 | 더 이상 관계를 이어갈 의사가 없는 경우 |

LLM은 사용자의 고백 및 수락·거절·보류 의도를 판단한다.

게임 로직은 LLM이 판단한 의도와 현재 점수, 대화 맥락을 종합하여 최종 엔딩을 결정한다.

점수만으로 엔딩을 확정하지 않으며, 실제 대화의 흐름과 관계 상황을 함께 반영한다.

### 3-10. 테스트 및 밸런스 조정 정책

현재 설정된 모든 점수와 조건은 개발 단계에서 사용하는 초기 테스트 기준이다.

실제 플레이 테스트를 통해 다음 항목을 확인하고 조정한다.

- 초기 호감도 및 신뢰도
- 에피소드별 해금 점수
- 게임 종료 최하점 기준
- 고백 가능 점수 및 고백 발생 빈도
- 캐릭터 유형별 난이도 차이
- 대화에 따른 점수 변화량
- 에피소드 재도전 빈도
- 최종 엔딩별 발생 비율

따라서 초기 점수, 에피소드 해금 조건, 고백 기준 및 게임 종료 조건은 최종 확정값이 아니다.

실제 플레이 테스트 결과에 따라 변경될 수 있으며, Type A와 Type B의 난이도 및 관계 발전 속도도 함께 조정한다.

## 4. LLM 분석 데이터 및 응답 구조

### 4-1. LLM 분석 항목

사용자의 발언과 이전 대화 맥락을 바탕으로 다음 정보를 분석한다.

- emotion: 사용자 발언의 감정
- behavior: 사용자의 대화 행동
- preference_match: 캐릭터 취향과 일치하는 정도
- dislike_match: 캐릭터가 싫어하는 요소와 일치하는 정도
- empathy: 공감 정도
- interest: 관심 표현 정도
- sincerity: 진정성 정도
- context_match: 이전 대화 맥락과의 일치 정도
- repetition_count: 반복적인 발언이나 행동의 횟수
- previous_affection: 이전 호감도
- previous_trust: 이전 신뢰도

위 분석 결과 중 머신러닝 모델에 필요한 9개 특징값을 구성한다.

### 4-2. 머신러닝 입력 JSON 예시

```json
{
  "personality_type": "A",
  "emotion": "positive",
  "behavior": "compliment",
  "preference_match": 0.8,
  "dislike_match": 0.0,
  "empathy": 0.9,
  "interest": 0.8,
  "sincerity": 0.9,
  "context_match": 0.8,
  "repetition_count": 0,
  "previous_affection": 20,
  "previous_trust": 20
}
```

### 4-3. 캐릭터 응답 구성

LLM은 다음 요소를 고려하여 응답을 생성한다.

1. 캐릭터 페르소나
2. 이전 대화 맥락
3. 현재 에피소드와 장소
4. 사용자의 발언과 감정
5. 현재 호감도와 신뢰도
6. 캐릭터의 관계 상태

캐릭터 응답은 분석 결과와 별도로 자연스러운 대화 형태로 생성한다.

## 5. 학습 데이터 구성

### 5-1. 데이터셋 개요

현재 학습 데이터는 총 560개 행으로 구성한다.

| 구분 | 데이터 수 |
|---|---:|
| Type A | 280개 |
| Type B | 280개 |
| 전체 | 560개 |

데이터는 LLM을 활용하여 생성하고, 유사도 기반 중복 검사와 Excel 수동 검토를 거쳐 구성한다.

### 5-2. CSV 데이터 컬럼

## 8. AI 모델과 게임 DB 연동 설계

### 8-1. 연동 기본 방향

현재 Streamlit 테스트 앱에서는 세션 상태를 활용하여 대화 내용과 점수를 관리한다.

실제 게임에 연동할 때는 기존 게임 DB의 구조를 먼저 확인한 뒤, 대화 기록과 관계 상태를 불러오고 저장하는 방식으로 구성한다.

DB 테이블과 컬럼은 기존 게임 DB를 확인한 후 매핑한다. 아래 필드는 연동 설계를 위한 예시이며 실제 DB 구조로 확정된 것은 아니다.

### 8-2. DB 저장 데이터 예시

| 필드 | 설명 |
|---|---|
| record_id | 대화 기록 ID |
| user_id | 사용자 ID |
| session_id | 게임 세션 ID |
| character_id | 캐릭터 ID |
| personality_type | 캐릭터 성격 유형 |
| episode_id | 현재 에피소드 |
| turn_number | 대화 턴 |
| user_utterance | 사용자 발언 |
| ai_response | AI 응답 |
| previous_affection | 이전 호감도 |
| previous_trust | 이전 신뢰도 |
| current_affection | 현재 호감도 |
| current_trust | 현재 신뢰도 |
| created_at | 기록 생성 일시 |

### 8-3. 머신러닝 특징값 생성

LLM이 대화 내용을 분석하여 다음 6개 특징값을 생성한다.

- preference_match
- dislike_match
- empathy
- interest
- sincerity
- context_match

repetition_count는 대화 기록 또는 분석 결과를 활용하여 구성한다.

previous_affection과 previous_trust는 DB 또는 현재 게임 상태에서 가져온다.

입력값 범위는 다음과 같이 관리한다.

| 특징값 | 범위 |
|---|---|
| preference_match | 0~1 |
| dislike_match | 0~1 |
| empathy | 0~1 |
| interest | 0~1 |
| sincerity | 0~1 |
| context_match | 0~1 |
| repetition_count | 0~3 |
| previous_affection | 0~100 |
| previous_trust | 0~100 |

### 8-4. 현재 테스트 앱 처리 흐름

현재 Streamlit 테스트 앱에서는 다음 순서로 처리한다.

1. 사용자가 메시지를 입력한다.
2. 현재 캐릭터 정보, 대화 맥락, 이전 점수를 GPT에 전달한다.
3. GPT가 캐릭터 응답과 분석용 특징값을 생성한다.
4. 이전 호감도와 신뢰도를 추가하여 9개 입력 특징값을 완성한다.
5. 캐릭터 유형에 맞는 모델 서버에 입력값을 전달한다.
6. XGBoost가 호감도와 신뢰도 변화량을 각각 예측한다.
7. 예측값을 정수로 변환하여 현재 점수에 반영한다.
8. 점수는 0~100 범위로 제한한다.
9. 대화와 점수를 Streamlit 세션 상태에 저장한다.
10. 에피소드 종료 시 해금 조건 및 게임 종료 조건을 확인한다.

현재 테스트용 점수 서버 주소:

```text
http://127.0.0.1:8765
```

### 8-5. DB 연동 시 고려사항

실제 DB 연동 전 다음 항목을 확인해야 한다.

- 기존 게임 DB 테이블 및 컬럼 구조
- 사용자와 게임 세션 식별 방식
- 캐릭터 및 성격 유형 연결 방식
- 에피소드와 턴 정보 저장 방식
- 이전 대화 기록 조회 방식
- 호감도와 신뢰도 업데이트 방식
- 에피소드 재도전 시 점수 복구 방식
- 게임 종료 및 엔딩 결과 저장 방식

초기 단계에서는 모든 9개 특징값을 DB에 별도로 저장할 필요는 없다.

원본 대화, AI 응답, 턴 정보, 캐릭터 유형, 이전 점수 등을 저장하고 필요할 때 LLM을 통해 특징값을 다시 생성하는 방식도 고려할 수 있다.

| 구성 요소 | 담당 역할 |
|---|---|
| LLM | 캐릭터 페르소나 유지, 대화 생성, 대화 맥락 분석 |
| XGBoost | 대화에 따른 호감도 및 신뢰도 변화량 예측 |

## 11. 테스트 중 발생한 문제 및 해결 방법

### 11-1. 동일하거나 유사한 AI 응답이 반복되는 문제

- **문제:** 사용자가 "없어", "몰라"와 같은 짧은 답변을 반복하면 AI가 새로운 대화 주제를 제시하지 못하고 비슷한 질문이나 마무리 문구를 반복하는 현상이 발생함.
- **발생 원인:** 짧은 답변에 대한 대응 규칙이 프롬프트에만 의존하고 있어 AI의 반복 응답을 코드에서 감지하거나 제어하는 기능이 부족했음.
- **해결 방법:** 최근 AI 응답과 새 응답의 유사도를 비교하는 반복 감지 로직을 추가하고, 유사한 답변이 생성되면 재생성을 요청하도록 수정함. 또한 짧은 답변이 반복될 경우 대화 방향을 전환하고, 반복이 계속되면 캐릭터 유형에 맞는 대체 응답을 출력하도록 개선함.
